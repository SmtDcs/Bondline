# Contract v3: the customer registers the promise

Deployed on NEAR testnet as `claimable-promises.testnet`, made keyless, and run live: 17 transactions (12 deliberate refusals) and 42 checks, recorded in `fixtures/runs/v3-live-run.json`; `npm run verify:live-run:v3` re-reads them from the chain. Every v2 limit in [JUDGES.md](JUDGES.md#limits-and-trust) that is not about the shop's cooperation still applies.

## The limit it closes

On v1 and v2 a promise is claimable only if the shop's relayer calls `register_receipt`, so a shop that regrets a promise simply never registers it. On v3 the customer registers the TEE-signed reply themselves (`register_receipt_as_buyer`), and the contract still pays only for genuine replies of this shop's bot.

The signature is not in the chat response; it is fetched with `GET /v1/signature/{chat_id}`, a route that needs any valid API key but does not check who owns the chat. The signed text covers the request and response hashes, so the signature is useless without the exact bytes, which only the shop's server has.

## Self-made promises

The shop's system prompt is public, so a customer could call NEAR AI with that prompt and a manipulative message and claim a genuinely TEE-signed promise. v3 accepts a customer-registered receipt only for a request the shop's own server sent.

The shop registers an ed25519 shop-auth key with `set_shop_key` (1 yoctoNEAR). `register_order` requires one (`ERR_NO_SHOP_KEY`) and copies it into the order, so rotating the key later cannot void an authorization already given. The bot server puts one tag into the system prompt of every request:

```
SHOP_AUTH|v3|contract=<id>|merchant=<id>|order=<id>|buyer=<id>|nonce=<32 hex>|sig=<128 hex>
```

`sig` is the shop key's signature over `"cbp-v3-shop-auth:" + hex(sha256(request bytes with the 128 sig characters set to '0'))`, so it covers the model, system prompt, history, the customer's message and the nonce.

`register_receipt_as_buyer(merchant, order_id, request_b64, signed_text, signature_hex, signer_public_key_hex)` checks, in order: the caller is the order's buyer (`ERR_NOT_BUYER`); the order is open and unexpired; the request is at most 32 KiB; the v2 TEE rules; `sha256(request_b64)` equals the signed request hash (`ERR_REQUEST_HASH_MISMATCH`); exactly one tag in the raw request (`ERR_SHOP_AUTH_MISSING`, `_MULTIPLE`, `_FORMAT`); the tag's contract, merchant, order and buyer (`ERR_SHOP_AUTH_CONTRACT`, `_MERCHANT`, `_ORDER`, `_BUYER`); the shop signature against the order's key (`ERR_SHOP_AUTH_SIGNATURE`); one customer receipt per authorized request (`ERR_SHOP_AUTH_USED`); no existing receipt for the reply (`ERR_RECEIPT_EXISTS`).

Unit tests refuse no tag, a tag signed by another key, the shop's real tag copied into a rewritten prompt, a tag for another buyer, contract, merchant or order, a second tag hidden in the customer's message, a malformed tag, a rotated key for an order created under the old one, the same authorized request twice, and a second reply to an already registered request. The promise token, the `max_bps` cap, the reservation, expiry and once-per-order claim are the v2 code, unchanged.

## Withheld signatures

The v3 bot server returns the full signed bundle with every reply, whether or not the relayer registers it; with `RELAYER_REGISTERS=0` it registers nothing. The page shows `signed bundle received` or a red `NO SIGNED BUNDLE`, and offers Register it myself when `preview_register_as_buyer` would accept the reply. The customer can also re-fetch the signature with their own key: `npm run customer:register -- <bundle.json> --merchant <shop> --contract <v3> --refetch-signature` with `CUSTOMER_NEARAI_API_KEY`.

The shop's server is still the only source of the exact bytes. A dishonest shop has to modify its server to send replies without a bundle, and the customer sees that on the very reply that should have carried it.

## Other changes from v2

Receipts are keyed by (merchant, order, response hash), so the same reply under another order cannot be claimed there. A shop registration never uses up the customer's authorization, so resampling does not stop the customer registering the real reply. The customer path charges the buyer's storage balance, which anyone can fund.

`new` refuses `owner == the contract account` (`ERR_OWNER_IS_CONTRACT`), and ownership moves in two steps (`propose_owner`, `accept_owner`). The owner manages only the signer list, and nothing needs the contract account to sign after `new`, so its only full-access key was deleted. `get_config` reports `api: 3`, `pending_owner` and `max_request_bytes` (32768); events are version `1.2.0`, with `registered_by` on `receipt_registered`, `shop_key` on `order_registered`, and new `shop_key_set`, `owner_proposed`, `owner_changed`. New views are `get_shop_key(merchant)`, `is_auth_used(merchant, order_id, request_hash)` and `preview_register_as_buyer(...)`, where null means it would be accepted, else the error code. v3 is ed25519 only.

## Trust on v3

| Who | Trusted for | No longer trusted for |
| --- | --- | --- |
| Shop / relayer | running the bot server, tagging each request and handing over the bundle; each order's expiry | deciding whether a reply its bot made gets registered; quietly withholding one reply; voiding an authorization by rotating its key; blocking a reply by filing it under another order |
| Shop-auth key holder | signing only requests the shop's server really sends | a leaked key lets the buyer of an order that carries it make self-made promises for that order, each still capped by `max_bps` and claimable once |
| Customer | nothing new | registering a reply the shop's bot did not produce for this order and this buyer |

What remains: the customer can resend the authorized request bytes to NEAR AI to pick a better reply, one receipt per request, which is the same power as asking the bot again inside the shop's prompt; the shop sets `ttl_ms` and the customer must register and claim before it; the independent re-fetch depends on NEAR AI keeping signatures, which is undocumented; and the customer needs a storage balance, about 0.01 NEAR for several receipts, plus a key that can call `claim`.

## Live run on testnet

Contract `claimable-promises.testnet`, owner `claimable-owner.testnet`, token `claimable-tusdc.testnet` (a fresh mock instance), shop `claimable-shop.testnet`, buyer `claimable-buyer.testnet`. The v1/v2 `*sm1110*` accounts were not touched; an earlier deployment, `claimable-v3.testnet`, is retired. Setup created the accounts, deployed and ran `new`, registered everything on the token, added the TEE signer, set the shop key, added two function-call keys and deleted the contract account's key; hashes are in `fixtures/runs/v3-live-run.json`.

Orders `A123-33` (honest bot) and `A124-33` (naive prompt) for 20 tUSDC, `max_bps` 3000, two-hour expiry, with the relayer registering nothing.

| what | result |
| --- | --- |
| the honest bot promised 20%, the shop did not register it, the customer did | accepted, `registered_by: claimable-buyer.testnet` |
| the customer claims from the bond | paid 4 tUSDC at 2000 bps |
| second claim on the same order | `ERR_ALREADY_CLAIMED` |
| self-made request with no shop tag | `ERR_SHOP_AUTH_MISSING` |
| self-made request with a tag the customer signed herself | `ERR_SHOP_AUTH_SIGNATURE` |
| the `A123-33` authorization used under `A124-33` | `ERR_SHOP_AUTH_ORDER` |
| a stranger registers the buyer's reply | `ERR_NOT_BUYER` |
| a receipt on the claimed order | `ERR_ORDER_NOT_OPEN` |
| the naive bot's genuine 100% promise, registered by the customer | accepted, paid 6 tUSDC at the cap |
| the same authorized request again | `ERR_SHOP_AUTH_USED` |

Before the customer acted, `get_receipt` was null and `preview_register_as_buyer` returned null. With a key that is not the shop's, the customer re-fetched the key-step signature by chat id, and text, signer and signature match the bundle. Later orders (`A123-35` / `A124-35`, `A123-34` / `A124-34`) repeated the refusals, including a shop-signed request naming another buyer (`ERR_SHOP_AUTH_BUYER`), and after expiry both a never-registered promise and a claim of a registered one gave `ERR_ORDER_EXPIRED`. The genuine 100% reply on `A124-34` was accepted before expiry.

Not run live, unit tests only: a tag for another contract or merchant, a rotated shop key, resampling. Earlier passes on the retired `claimable-v3.testnet`, and one on `A123-32` / `A124-32` whose first check compared against a stale file hash, are not part of the record.

## Reproduce the run

`RUN=<n> TTL_MS=7200000 CONTRACT_ID=claimable-promises.testnet node app/scripts/demo-setup-v2.mjs` registers the two orders; the shop key must already be set and `TTL_MS` at least one hour. Start the app with `CONTRACT_ID=claimable-promises.testnet RELAYER_REGISTERS=0 DEMO_ORDERS="A123-<n>:Broken mug:2000,A124-<n>:Late delivery:2000:naive" npm run dev`, then `RUN=<n> node app/scripts/live-v3.mjs V1 V2 V3 V4 V5 V6`. V6 needs `CUSTOMER_NEARAI_API_KEY`, a key that is not the shop's; `CBP_STRANGER_ACCOUNT` / `CBP_STRANGER_KEY` name the wrong-buyer account.

The later checks need `RUN=<m> TTL_MS=7200000` with `RUN2=<m> node app/scripts/live-v3.mjs V7 V8` (V7 needs `CUSTOMER_NEARAI_API_KEY`, V8 `SHOP_AUTH_SEED_HEX`), and an expiry run with `RUN=<e> TTL_MS=3600000`, `EXP_RUN=<e> node app/scripts/live-v3.mjs V9`, then `V10` after the hour. `DEMO_ORDERS` must list those orders.

Deploying a fresh v3: `node app/scripts/deploy-v3.mjs` prints the plan; add `--send`, then `--send --lock`.
