# Contract v3: the customer registers the promise

**Status:** deployed on NEAR testnet as `claimable-promises.testnet`, made keyless, and run live: 17 transactions (12 deliberate
refusals) and 42 checks, all passed, recorded in `fixtures/runs/v3-live-run.json`. `npm run verify:live-run:v3` re-reads every
transaction from the chain. Every v2 limit in [HACKATHON.md](HACKATHON.md#limits-and-trust) that is not about the shop's cooperation still applies to v3.

## The limit it closes

On v1 and v2 a promise is claimable only if the **shop's** relayer calls `register_receipt`. A shop that regrets a refund promise
simply does not register it, and the shopper is left with NOT A PROMISE. On v3 the **customer** registers the TEE-signed reply
themselves (`register_receipt_as_buyer`), and the contract still pays only for genuine replies of **this shop's bot**.

## Who can fetch a NEAR AI signature

From the NEAR AI Cloud docs (https://docs.near.ai/cloud/verification/cloud-api/response-signatures.md) and the gateway source
(github.com/nearai/cloud-api, `crates/api/src/routes/attestation.rs` at commit `f591279b8ab1086716887bd49df618eb155a4317`), read on 2026-11-12:

- The signature is not in the chat completion response. It is fetched afterwards with `GET /v1/signature/{chat_id}`.
- That route needs a valid API key but does not check that the key owns the chat, so **any** NEAR AI Cloud key can fetch the
  signature of any chat id.
- The signed text is `<model>:sha256(request bytes):sha256(response bytes)`. To use it the customer also needs the **exact** request
  and response bytes, which only the shop's server has.
- No retention period for signatures is documented.

So the customer needs the bytes from the shop's server, and can get the signature either from that server or independently.

## Trap 1: self-made promises

The shop's system prompt is public (it is in every bundle). Without more, a customer could call NEAR AI directly with that prompt and
a manipulative message, get a genuinely TEE-signed "promise" and claim it. v3 accepts a customer-registered receipt only for a request
**the shop's own server sent**:

- The shop registers a **shop-auth key** (ed25519) with `set_shop_key` (1 yoctoNEAR). `register_order` requires one
  (`ERR_NO_SHOP_KEY`) and **copies it into the order**, so rotating the key later cannot void an authorization already given.
- The bot server puts one tag into the system prompt of every request it sends:
  `SHOP_AUTH|v3|contract=<id>|merchant=<id>|order=<id>|buyer=<id>|nonce=<32 hex>|sig=<128 hex>`.
  `sig` is the shop key's signature over `"cbp-v3-shop-auth:" + hex(sha256(request bytes with the 128 sig characters set to '0'))`,
  so it covers the whole request: model, system prompt, history, the customer's message and the nonce.
- `register_receipt_as_buyer(merchant, order_id, request_b64, signed_text, signature_hex, signer_public_key_hex)` checks, in order:
  the caller is the order's buyer (`ERR_NOT_BUYER`); the order is open and not expired; the request is at most 32 KiB; the v2 TEE rules
  (known, unexpired signer, model, `env::ed25519_verify`); `sha256(request_b64)` equals the signed request hash
  (`ERR_REQUEST_HASH_MISMATCH`); exactly one tag in the raw request (`ERR_SHOP_AUTH_MISSING` / `_MULTIPLE` / `_FORMAT`); the tag's
  contract, merchant, order and buyer (`ERR_SHOP_AUTH_CONTRACT` / `_MERCHANT` / `_ORDER` / `_BUYER`); the shop signature against the
  **order's** key (`ERR_SHOP_AUTH_SIGNATURE`); one customer receipt per authorized request (`ERR_SHOP_AUTH_USED`); no existing receipt
  for the same reply (`ERR_RECEIPT_EXISTS`).
- Refused in unit tests (synthetic vectors in `contract-v3/tests/v3_vectors.json`): no tag, a tag signed by any other key, the shop's
  real tag copied into a rewritten prompt, a tag for another buyer / contract / merchant / order, a second tag smuggled into the
  customer's message, a malformed tag, a tag by a rotated key for an order created under the old one, the same authorized request
  twice, and a second reply to an already registered authorized request.
- The promise token, the `max_bps` cap, the reservation, expiry and once-per-order claim are the v2 code, unchanged.

## Trap 2: withheld signatures

- **Automatic route:** the v3 bot server returns the full signed bundle (request and response bytes, chat id, TEE signature, signer,
  shop-auth nonce and key) **with every reply**, whether or not the relayer registers it and even when that registration fails.
  With `RELAYER_REGISTERS=0` it registers nothing (the uncooperative shop, for the demo). The page shows `signed bundle received` on
  every v3 reply, or a red `NO SIGNED BUNDLE`, and offers **Register it myself** when the contract's `preview_register_as_buyer`
  view would accept the reply.
- **Independent route:** the customer re-fetches the TEE signature with **their own** NEAR AI key and compares it:
  `npm run customer:register -- <bundle.json> --merchant <shop> --contract <v3> --refetch-signature` (`CUSTOMER_NEARAI_API_KEY`).
- **What stays trusted:** the shop's server is the only source of the exact bytes. A shop that wants to withhold them has to modify its
  server to send replies without a bundle (or with one the contract refuses). The customer sees that on the very reply that should have
  carried it; what they cannot do is force a dishonest server to hand over bytes it never sends.

## Other changes from v2

- **Receipts keyed by (merchant, order, response hash).** On v2 a receipt filed under the wrong order blocked that reply for good. On v3
  the same reply under another order is a separate record that cannot be claimed there.
- **Shop registrations never use up the customer's authorization.** A shop that resamples the request and registers a reply it prefers
  does not stop the customer from registering the real one.
- **Storage:** the customer path charges the **buyer's** storage balance (anyone can fund it with `storage_deposit`), so a shop emptying
  its own balance cannot block the customer.
- **Owner and keyless deployment:** `new(owner, …)` refuses `owner == the contract account` (`ERR_OWNER_IS_CONTRACT`); ownership moves in
  two steps (`propose_owner`, `accept_owner`, 1 yoctoNEAR each). The owner manages only the signer list. Nothing needs the contract
  account to sign after `new`, so its only full-access key was deleted: nobody can redeploy or act as the account, and there is no upgrade
  method.
- `get_config` reports `api: 3`, `pending_owner` and `max_request_bytes` (32768). Events are version `1.2.0`; `receipt_registered` names
  `registered_by`, `order_registered` the `shop_key`; new events `shop_key_set`, `owner_proposed`, `owner_changed`.
- New views: `get_shop_key(merchant)`, `is_auth_used(merchant, order_id, request_hash)`, `preview_register_as_buyer(...)` (null = would
  be accepted, else the error code; it does not check the buyer's storage balance).
- v3 is ed25519 only (v2's optional, never deployed ECDSA module is gone).

## Trust on v3

| Who | Trusted for | No longer trusted for |
| --- | --- | --- |
| Shop / relayer | running the v3 bot server (tagging each request, handing over the bundle); each order's expiry | deciding whether a reply its bot made gets registered; quietly withholding one reply; voiding an authorization by rotating its key; blocking a reply by filing it under another order |
| Shop-auth key holder | signing only requests the shop's server really sends | n/a: a leaked key lets the **buyer** of an order that carries it make self-made promises for that order, each still capped by `max_bps` and claimable once |
| Customer | nothing new | registering a reply the shop's bot did not produce for **this** order and **this** buyer |

Limits that remain:

- **Resampling:** the customer has the authorized request bytes, so they can send them to NEAR AI again and register the reply they
  like best (one customer receipt per authorized request). That is the same power as asking the bot again, inside the shop's own
  prompt and capped by `max_bps`.
- **Expiry:** as on v2, the shop sets `ttl_ms` (floor `min_order_ttl_ms`); the customer must register and claim before it.
- **Signature retention:** the independent re-fetch depends on NEAR AI keeping signatures, which is undocumented. The live run fetched
  each one moments after the reply.
- **The customer needs a storage balance on the contract** (about 0.01 NEAR covers several receipts) and a key that can call `claim`
  and `register_receipt_as_buyer`.

## Reproduce the run

`RUN=<n> TTL_MS=7200000 CONTRACT_ID=claimable-promises.testnet node app/scripts/demo-setup-v2.mjs` registers the two orders (the shop
key must already be set; `TTL_MS` must be at least one hour). Start the app with `CONTRACT_ID=claimable-promises.testnet
RELAYER_REGISTERS=0 DEMO_ORDERS="A123-<n>:Broken mug:2000,A124-<n>:Late delivery:2000:naive" npm run dev` and run
`RUN=<n> node app/scripts/live-v3.mjs V1 V2 V3 V4 V5 V6` (V6 needs `CUSTOMER_NEARAI_API_KEY`, a NEAR AI key that is not the shop's).
`CBP_STRANGER_ACCOUNT` / `CBP_STRANGER_KEY` name the account for the wrong-buyer check.

The later checks: a second run with `RUN=<m> TTL_MS=7200000` (`RUN2=<m> node app/scripts/live-v3.mjs V7 V8`) and an expiry run with
`RUN=<e> TTL_MS=3600000` (`EXP_RUN=<e> node app/scripts/live-v3.mjs V9`, then after the hour `EXP_RUN=<e> node app/scripts/live-v3.mjs V10`);
the app's `DEMO_ORDERS` must list those orders. V7 needs `CUSTOMER_NEARAI_API_KEY`, V8 needs `SHOP_AUTH_SEED_HEX`.

Deploying a fresh v3: `node app/scripts/deploy-v3.mjs` (prints the plan), `--send`, then `--send --lock`.
